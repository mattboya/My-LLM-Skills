# Unattended startup and recovery

Read this when `auto` is in the invocation, in Claude Code, Codex or Antigravity. `auto` authorizes routine local preparation and repair as well as recommended answers and Go. An uncommitted working tree is input to preserve, not a reason to end the run or ask the user to commit it.

## Choose the run checkout before planning

1. Locate the source queue and newest saved wave doc first. A RUNNING doc, including an auto-checkout pointer, means resume its recorded repo, branch, base, scratchpad and host. A source pointer marked `**Auto preparation:** PREPARING` means retry its recorded preparation spec; the run doc may not exist yet, so this is not a completed plan and not a reason to start a second snapshot. Preserve/reconcile writers using the client's recovery procedure. Do not snapshot an active run again, require its current agent edits to be clean, or repeat completed work. If the host stopped for a recoverable local issue, diagnose and repair it in the same parent turn, then resume it; an internal host failure is not an instruction to ask the user to restart. **Preflight-only interruption:** Go sets RUNNING before Wave 0, so that status alone does not prove implementation agents started. When logs/recorded IDs, absent lane/implementation host run state and the commit range prove it stopped before implementation dispatch with no Wave implementation commits or live writers, continue its existing scope/Answers through step 2's preparation. Completed read-only planning hosts/IDs are evidence to retain, not implementation dispatch. Keep the same wave identity and scratchpad; refresh the copied plan for the checkpoint. If any live writer or lane/implementation host state exists, reconcile it instead of assuming an unstarted run.
2. For a fresh, unstarted or proven preflight-only wave, read the source status. A clean source can use its existing checkout. A dirty source uses `prepare-auto.mjs`, even if the protocol was written for one shared checkout: the **parent** prepares one isolated checkout, then all agents share that checkout under the usual ownership/lock rules. The original checkout's files, staged/unstaged split and branch history remain intact.
3. Write a spec JSON to the scratchpad with absolute paths:

   ```json
   {
     "repo": "/absolute/source/repo",
     "checkout": "/absolute/scratchpad/auto-checkout",
     "manifest": "/absolute/scratchpad/auto-checkout.json",
     "copy": ["existing-wave-doc.md", "existing-wave.queue.md"]
   }
   ```

   Use an unused destination outside the source working tree. `copy` names any existing ignored wave docs/queue snapshots needed to pick up a PLANNED or proven preflight-only RUNNING run, retaining its full scope and Answers; omit absent ones. **Before calling the helper**, safely write a source-side wave pointer with Status PLANNED, `**Auto preparation:** PREPARING`, source/run paths, spec path, manifest, scratchpad and intended run doc. This discoverable pointer is separate from any existing full plan. Then run `node ~/.agents/skills/wave/prepare-auto.mjs "<spec.json>"`. It uses a temporary index to checkpoint the working-tree versions of tracked files (including force-added ignored files) and nonignored untracked files, creates a local `codex/wave-auto-*` branch in a separate worktree, and copies the ignored queue/control files from durable backups. It does not stash, reset, commit onto, or clean the source branch. Ignored dependencies, build artifacts and environment files are not bulk copied. Optional setup diagnostics use `WAVE_AUTO_DEBUG=1`.
4. Set `{REPO}`/`args.repo`, branch and `{BASE}` to the returned checkout, branch and checkpoint. Build an **effective run protocol** with paths/branch adjusted to that checkout; record these adjustments and the manifest in the wave doc. Preserve the source protocol's ownership, test, ticket and no-push rules. The original branch's WIP is the base, not a shipped Wave change. All planners, builders, snapshots, helpers, gates and commits use the run checkout. If a saved PLANNED doc was copied, refresh its base/prototypes against the captured source content; do not edit a native host's already-started args.
5. Prepare the runtime from the protocol: reuse installed dependencies where compatible, link read-only dependency directories when safe, copy only the named runtime inputs, and run existing setup commands that need no new external approval. A hardcoded source path in a test/helper must be adapted to the run checkout. Ignore rules can live in the common Git exclude file; do not dirty the source code merely to ignore Wave artifacts. If the helper's preparation was interrupted, rerun its same spec: it recovers the checkpoint/inputs; once ready, it reuses the checkout without replacing its queue, commits or writers' edits.
6. Keep the source pointer's Auto preparation field PREPARING through setup/planning; a resumed PREPARING pointer reuses the recorded spec and existing checkout before continuing any unfinished plan. Before Go, finish its links to the full run doc. At auto Go, both pointer and run doc get RUNNING and the same In flight IDs, and Auto preparation becomes READY; at handoff, both record the final state. These queue/control-doc updates use the usual backups and safe writes. They make a later invocation in the source repo find the existing run instead of launching a duplicate. Tell the user where work is running in a progress update; continue without waiting for their response.

## Recover preflight conditions without another user turn

- **Missing protocol:** reuse one from another checkout when possible. Otherwise derive it from repo instructions/config/CI as step 0 specifies and record the conservative defaults under the auto Answers. Tickets: `none…` (queue IDs as keys, with `QUEUE_IDS.txt`) only when the queue header's Tracker line says none; otherwise, with tracker details unknown, ticket `none` and file nothing (SKILL.md Wave 0 step 4). Preserve no-push and never-Done, use the repo's existing identity (Codex co-author default from the adapter when absent), and infer gates from existing configured commands. Record uncertainty rather than inventing credentials, permissions or deployments. The automatic Go covers this local draft.
- **Baseline gates red:** save the original outputs and classify them before dispatch. Repair local setup or an in-scope defect in the run checkout, using existing dependencies and test-first changes for code. Keep preflight fixes separate in commits/reports. An unresolved baseline failure becomes recorded evidence, with directly affected units/dependents held; continue independent Ready work whose targeted gates can be meaningfully verified. Pass known failures in the lane args as `baselineFailures: [{gate, evidence, scope, heldItems}]`, with scope `in-wave` or `outside-wave`, and record the same evidence in the wave doc. The runner carries this classification to builders/reviewers/final gates, keeping unrelated baseline repair outside the approved scope. Final gates still report actual failures; never claim allGreen by excluding a failed gate. Stop only when no scoped unit can make meaningful progress, not because any baseline gate is red.
- **Fetch or tracker unavailable:** record the limitation and use local refs where the work remains verifiable; an unreachable tracker means ticket `none`, never queue IDs (SKILL.md Wave 0 step 4). Defer unavailable external updates to the handoff. Routine local work continues.
- **Preparation/agent failure:** preserve work and logs, diagnose, make a bounded repair and resume in this same parent turn. Use at most two recovery attempts for the same unchanged failure; stop retrying that failure and continue independent work if possible. Resolve a source still changing during snapshot capture with a fresh capture attempt; never overwrite a live writer. Unresolved external permissions, missing required resources, or a failure that prevents every scoped unit from being tested remain genuine blockers and are reported honestly.

## Handoff

Report the completed run branch, checkout, preserved source branch, checkpoint and verification status. Keep the run checkout and evidence; no automatic push, merge into the dirty source, or archive of unfinished work. The run's wave commits are the range after its checkpoint, excluding the WIP checkpoint. Use the existing queue harvest/safe-write procedure to reconcile shipped entries and mid-run source changes back into the source queue; retain follow-up entries and held answers. This metadata reconciliation is automatic, not a request for the user to restart the wave. Open the run's review/results in the app when supported. If verification is partial, say so in both wave docs rather than marking unfinished scope shipped.
